PATH-G1 전체 파이프라인 정리
작성 기준: 2026-08-04, 현재 /home/url/PATH-G1 코드 기준

이 문서는 현재 PATH 프로젝트에서 실제로 연결되어 있는 제어, 비전, belief inference,
shared control 흐름을 한 파일에서 확인하기 위한 요약이다. 실행 명령을 새로 켜는
문서가 아니라, 현재 프로세스 간 데이터가 어떻게 흘러가는지를 정리한 것이다.


0. 전체 데이터 흐름 요약
==========================

G1 RGB-D bridge
  -> LCM: G1_CAMERA_FRAME, G1_DEPTH_FRAME, G1_CAMERA_CALIBRATION
  -> Thor remote gateway
  -> Wi-Fi LCM: PATH_REMOTE_RGB_FRAME, PATH_REMOTE_DEPTH_FRAME,
                PATH_REMOTE_CAMERA_CALIBRATION, PATH_REMOTE_ROBOT_STATE
  -> 외부 desktop remote YOLO11-seg worker
  -> Wi-Fi LCM: PATH_REMOTE_PERCEPTION_RESULT, PATH_REMOTE_OVERLAY_JPEG,
                PATH_REMOTE_PERCEPTION_HEARTBEAT
  -> Thor gateway result validation / EE target republish
  -> ZMQ: tcp://127.0.0.1:5564, topic path_static_ee_target
  -> PATH state machine bridge
  -> CasADi/IPOPT arm target solve
  -> ZMQ: tcp://127.0.0.1:5560, topic path_qp_reference
  -> SONIC deploy runtime dynamic reference
  -> G1_POLICY_ACTION / PD target output

PICO / XR teleop
  -> PICO manager / calibrated wrist pose stream
  -> ZMQ: tcp://127.0.0.1:5566, vr_pose_debug
  -> PATH state machine bridge
  -> q/e 모드의 사용자 wrist target으로 사용

SONIC
  -> lower body / balance / locomotion policy owner
  -> PATH는 하체 root command를 직접 제어하지 않고, trained default standing
     height sentinel height=-1.0과 zero movement command를 사용한다.


1. 제어기: arm(XR teleop) + waist/lower body(SONIC)
===============================================

1.1 주요 프로세스
----------------

1) PICO manager
   - 위치: path_streaming/pico_manager_thread_server.py
   - 역할:
     - PICO / XR 입력을 읽는다.
     - 현재 주력 경로에서는 manager-calibrated wrist SE(3)를 vr_pose_debug로 낸다.
   - 주요 출력:
     - tcp://127.0.0.1:5566 / vr_pose_debug
       왼손/오른손 wrist target SE(3), pelvis/waist 기준으로 보정된 teleop target.
     - tcp://127.0.0.1:5565 / pico_button_event
       q/w/e/r 등 state machine button event.
     - tcp://127.0.0.1:5559
       legacy pose/command/manager_state stream. 현재 arm target 주력 경로는
       이 raw SMPL/GMR fallback이 아니라 vr_pose_debug 직접 사용이다.

2) PATH state machine bridge
   - 위치: path_streaming/path_state_machine_bridge.py
   - 실행 wrapper: scripts/run_state_machine_bridge.sh
   - 기본 control rate: 50 Hz
   - CPU pinning 기본값: taskset -c 6-7
   - 역할:
     - q/w/e/r state 전환을 받는다.
     - PICO wrist target과 perception static target을 받는다.
     - arms에 대해서 CasADi/IPOPT bimanual IK target을 만든다.
     - SONIC manager port로 planner/command/manager_state를 보낸다.
     - dynamic arm reference를 path_qp_reference로 보낸다.

3) SONIC deploy runtime
   - 위치:
     - real LCM: path_deploy/scripts/run_path_lcm.sh
     - Mujoco: path_deploy/scripts/run_path_mujoco.sh
   - 역할:
     - lower body, balance, locomotion policy의 owner.
     - dynamic reference transport를 통해 PATH arm target을 받아 policy/action 쪽에 반영.
   - real LCM output:
     - LCM action channel: G1_POLICY_ACTION
     - LCM state channel: G1_ROBOT_STATE

4) CasADi/IPOPT arm solver
   - 위치: path_planning/unitree_arm_nonlinear_ik.py
   - 역할:
     - 29-DoF 전체 모델 중 실제 decision variable은 14-DoF arm joint.
     - legs, waist, hands는 locked/frozen model로 둔다.
     - q/e 모두 같은 arm solve 경로를 사용하되, e에서는 shared target blending이 들어간다.


1.2 입력
--------

state machine bridge 입력:

- PICO calibrated wrist target:
  - endpoint: tcp://127.0.0.1:5566
  - topic: vr_pose_debug
  - 의미: 사용자의 좌/우 wrist target SE(3). 현재 arm teleop의 authoritative input.

- PICO button:
  - endpoint: tcp://127.0.0.1:5565
  - topic: pico_button_event
  - 의미: q/w/e/r mode transition, grip trigger 등.

- Perception/static EE target:
  - endpoint: tcp://127.0.0.1:5564
  - topic: path_static_ee_target
  - 의미: vision/belief가 선택한 물체 중심 또는 접촉점의 pelvis_identity_fk 좌표.

- SONIC high-level planner command로 들어가는 값:
  - mode: idle/planner conditioning
  - movement: [0, 0, 0]
  - facing: [1, 0, 0]
  - speed: -1.0
  - height: -1.0
  - height=-1.0은 PATH가 base height를 0으로 넣는 값이 아니라,
    SONIC trained default standing height를 사용하라는 sentinel이다.

- Robot state:
  - real: LCM G1_ROBOT_STATE
  - state machine / FK / shared control에서 현재 wrist FK와 mode 상태 확인에 사용.


1.3 출력
--------

state machine bridge 출력:

1) SONIC manager input
   - endpoint: tcp://127.0.0.1:5556
   - topics: pose, command, planner, manager_state
   - 목적:
     - SONIC policy에는 하체/balance와 policy phase를 유지할 입력을 제공.
     - lower body q[0:12]는 freeze/zero conditioning.
     - waist q[12:15]는 identity/zero conditioning.
     - raw SMPL lower body나 raw waist motion을 그대로 넣지 않는다.

2) PATH dynamic arm reference
   - endpoint: tcp://127.0.0.1:5560
   - topic: path_qp_reference
   - schema:
     - path.ipopt_arm_reference.v1
     - arm_target_owner=casadi_ipopt
     - solver_backend=casadi_opti_ipopt
   - 내용:
     - q_ref 29-DoF 형태.
     - 실제 arm target은 IPOPT가 푼 14-DoF arms가 채워진다.
     - lower/waist는 policy conditioning과 충돌하지 않게 frozen/neutral.

SONIC deploy output:

- real G1:
  - G1_POLICY_ACTION LCM으로 최종 policy/action/PD target 출력.
- Mujoco:
  - Mujoco action/PD target으로 동일한 dynamic reference 흐름 검증.


1.4 mode별 동작
---------------

q / teleop
  - 목적: 순수 teleoperation.
  - 입력: PICO calibrated wrist target.
  - belief/static object target은 사용하지 않는다.
  - alpha=0에 해당하는 개념으로, 사용자 wrist target만 arm objective가 된다.
  - e 모드와 같은 CasADi/IPOPT bimanual solve 경로를 사용하되, 물체 target blending은 없다.

w
  - 프로젝트 내 state transition/hold/중간 모드로 쓰인다.
  - 현재 arm control 주력 흐름은 q/e의 IPOPT 경로이다.

e / auto_planning, shared control
  - 목적: 사용자의 wrist target과 belief object/contact target을 blend.
  - 입력:
    - PICO wrist target: human reference
    - path_static_ee_target: object/contact target
  - 출력:
    - blended wrist target을 IPOPT로 풀어 arm q_ref 생성.

r / damped return
  - 목적: arm target을 현재 PICO body target 쪽으로 완만히 return.
  - SONIC은 계속 lower body owner.


1.5 waist / lower body ownership
--------------------------------

- PATH state machine bridge는 시작 시 다음을 강제한다.
  - freeze_planner_lower_body=True
  - freeze_planner_waist=True
  - shared_waist_mode=hold_identity
  - outer_waist_enabled=False

- 의미:
  - PATH는 raw PICO/SMPL lower body를 SONIC에 넣지 않는다.
  - planner conditioning으로 들어가는 waist는 identity/zero 기준이다.
  - lower body root command는 [0,0,0] movement와 height=-1.0 default-standing sentinel이다.
  - 실제 balance/standing은 SONIC policy가 담당한다.

[주의]
- q/e에서 arm은 PICO calibrated wrist SE(3) -> CasADi/IPOPT arm IK -> path_qp_reference 구조이다.
- real deploy에서 legacy in-process ProxQP는 쓰지 않고,
  --use-ee-qp flag는 dynamic reference transport/FK telemetry 호환용으로 유지되어 있다.
- shared control에서 orientation target은 operator의 입력으로 설정한다.
- waist는 SONIC bounded waist output을 유지할지는 real 안정성 기준으로 추가 검증 필요.

[미구현 / TODO]
- e 모드에서 target lost/null일 때의 fallback은 기본 자세 유지가 목표이나,
  remote belief worker가 null target을 어떤 schema로 보낼지 desktop 구현과 맞춰야 한다.


2. Vision module
================

2.1 Thor 내부에서 실험한 backend 요약
------------------------------------

SAM3
  - PyTorch / TensorRT backend를 모두 테스트.
  - TensorRT FP16으로 latency를 줄였지만, SONIC policy와 GPU를 공유할 때
    제어 delay와 thermal/over-current 문제가 생길 수 있음.
  - semantic prompt 기반이라 object prompt 설정에 민감하고, GPU cost가 큼.

SAM2
  - generic mask / central prompt 방식 후보로 남김.
  - SAM 계열이라 일반 mask 품질은 가능하지만, semantic label은 별도 로직 필요.

EfficientTAM
  - SAM2 스타일 tracking 구조 후보.
  - Thor에서 동작 검증했으나, post-processing과 candidate stability가 필요.

EfficientViT-SAM
  - lightweight SAM 후보로 실험했지만, 현재 주력에서는 제외하는 방향.

YOLO11-seg
  - COCO-80 semantic instance segmentation.
  - 현재 remote desktop offload의 주력 backend.
  - concept label filtering과 confidence >= 0.80 필터를 적용해 불필요한 mask를 줄임.


2.2 현재 주력: remote YOLO11 worker
----------------------------------

목표:
  - Thor의 GPU/CPU 부하를 줄이기 위해 segmentation을 외부 desktop에서 수행.
  - Thor는 G1과 control loop에 가까운 bridge/gateway만 유지.
  - vision/belief처럼 ms 단위 제어 안정성에 직접 들어가지 않는 heavy 작업을 Wi-Fi로 offload.

Thor side:
  - 파일: perception/remote_offload/thor_gateway.py
  - wrapper: perception/tools/run_thor_remote_gateway.sh
  - 역할:
    1. G1 LCM에서 RGB/depth/calibration/robot_state 수신.
    2. RGB/depth timestamp pair를 맞춤.
    3. Wi-Fi LCM remote channel로 frame forward.
    4. desktop worker의 result/heartbeat/overlay 수신.
    5. result freshness, timestamp, calibration_id, image size, sequence 검증.
    6. valid result에서 target_contact_goal_m 또는 center_goal_m을 선택.
    7. 선택 target을 path_static_ee_target ZMQ로 republish.

Desktop side:
  - 파일: perception/remote_offload/remote_yolo11_worker.py
  - 역할:
    1. Wi-Fi LCM remote RGB/depth/calibration/robot_state 수신.
    2. YOLO11-seg PyTorch inference.
    3. concept label filtering.
    4. confidence >= 0.80인 detection만 mask/track/belief 후보로 유지.
    5. aligned depth와 calibration으로 2-D mask를 3-D point/object로 변환.
    6. stable 3-D track id 생성.
    7. target center/contact candidate를 remote result로 송신.


2.3 LCM channel 구조
-------------------

G1/Thor local LCM:
  - G1_CAMERA_FRAME
    RGB JPEG frame.
  - G1_DEPTH_FRAME
    D435 depth frame.
  - G1_CAMERA_CALIBRATION
    D435 / VideoHub calibration.
  - G1_ROBOT_STATE
    G1 q/dq/IMU/state. depth self-filter와 FK, target transform에 사용.

Thor -> Desktop Wi-Fi LCM:
  - PATH_REMOTE_RGB_FRAME
  - PATH_REMOTE_DEPTH_FRAME
  - PATH_REMOTE_CAMERA_CALIBRATION
  - PATH_REMOTE_ROBOT_STATE

Desktop -> Thor Wi-Fi LCM:
  - PATH_REMOTE_PERCEPTION_RESULT
    MessagePack result. backend, frame timestamp, calibration_id, objects, masks,
    3-D center/contact point 포함.
  - PATH_REMOTE_PERCEPTION_HEARTBEAT
    worker alive/status.
  - PATH_REMOTE_OVERLAY_JPEG
    desktop/web viewer용 overlay image.


2.4 remote perception result schema 요약
---------------------------------------

PATH_REMOTE_PERCEPTION_RESULT:

- version
- sequence
- published_timestamp_us
- source_rgb_timestamp_us
- source_depth_timestamp_us
- calibration_id
- image_width, image_height
- backend
  - 현재 remote YOLO11: yolo11_pytorch
- inference_ms
- valid
- error
- objects[]

각 object:

- track_id
- label
- score
- box_xyxy
- mask_encoding=bitpack-zlib-row-major
- mask_data
- mask_height, mask_width
- median_depth_m
- center_pixel_uv
- center_camera_m
- center_goal_m
- valid_depth_points
- target_contact_goal_m
- contact_candidates[]

Thor gateway의 EE target 선택:

- label_filter와 min_score를 통과한 object만 후보.
- position_field:
  - contact: target_contact_goal_m만 사용.
  - center: center_goal_m만 사용.
  - auto: target_contact_goal_m 우선, 없으면 center_goal_m.
- 선택된 target은 다음 ZMQ로 변환:
  - endpoint: tcp://127.0.0.1:5564
  - topic: path_static_ee_target
  - coordinate_frame: pelvis_identity_fk
  - source: remote_yolo11_contact 또는 remote_yolo11_center
  - streaming_goal=True
  - confidence/object_confidence는 현재 object score 기반.


2.5 YOLO11 전처리 / 후처리
--------------------------

전처리:
  - RGB frame decode.
  - YOLO 입력 크기 imgsz=640.
  - web/CLI concept string을 comma-separated label list로 파싱.
  - concept가 비어 있으면 allowed_classes 설정과 excluded_classes 적용.
  - 현재 기본 excluded_classes에는 person 포함.

YOLO output filtering:
  - confidence >= 0.80만 object 후보로 진입.
  - threshold 미만 detection은 tracking fallback, belief, overlay 후보에 들어가면 안 됨.
  - max_masks로 후보 수 제한.
  - same-label / IoU / 3-D nearest 기반 track association으로 급격한 ghost 잔상 억제.

Mask post-processing:
  - 작은 mask 제거.
  - boundary erosion/crop 계열 후처리로 mask 외곽 3~5 px 정도의 불안정 boundary를 줄이는 방향.
  - missing track은 내부 재연결용으로만 유지하고, overlay/belief output에는 내보내지 않는 것이 목표.


2.6 depth based robot/self filter
---------------------------------

목표:
  - 로봇 손/팔/몸통이 segmentation candidate에 들어가지 않도록 제거.
  - 특히 로봇 손이 물체처럼 mask가 잡히는 문제를 줄임.

구현 위치:
  - perception/seg_web_node/depth_based_filter.py
  - YOLO11/SAM2/SAM3/EfficientTAM backend에서 공통 mixin처럼 사용.

입력:
  - aligned RGB/depth
  - depth_scale
  - camera intrinsics
  - camera->goal/pelvis transform
  - G1_ROBOT_STATE q
  - FK robot geometry approximation

처리:
  1. depth를 bilateral filter로 공간/깊이 smoothing.
  2. temporal IIR depth filter 적용.
     - temporal_alpha=0.35
     - temporal_reset_threshold_m=0.080
  3. G1 FK로 arm/wrist/torso collision primitive를 camera image에 render.
     - arm_radius_m=0.055
     - wrist_radius_m=0.075
     - torso_radius_m=0.090
     - padding_scale=1.05
     - sample_step_m=0.020
  4. robot depth buffer 생성.
  5. mask pixel이 robot surface와 depth상 겹치면 제거.

Depth hysteresis margin:

  - margin_low_m=0.030
  - margin_high_m=0.055

개념적으로:

  enter robot/self pixel:
    measured_depth >= robot_depth - margin_low_m

  hold robot/self pixel:
    measured_depth >= robot_depth - margin_high_m

margin_high > margin_low로 잡아, frame-to-frame depth noise 때문에 self-filter가
깜빡이는 것을 줄인다.

[주의]
- depth self-filter는 calibration과 robot_state freshness에 의존한다.
- calibration_id mismatch 또는 robot_state stale 상태에서는 self-filter 품질이 떨어진다.
- depth filter는 로봇 body 제거용이지, 모든 floor/desk surface 제거를 보장하지 않는다.

[미구현 / TODO]
- remote_yolo11_worker의 contact candidate 생성 경로는 desktop 구현과 함께 최종 확인 필요.
  현재 protocol은 contact_candidates와 target_contact_goal_m을 지원하지만,
  remote worker에서 belief까지 desktop에서 실행할지, Thor에서 result만 받아 belief를 실행할지
  최종 배치가 아직 완전히 고정되지 않았다.
- remote result에 object posterior와 joint_confidence를 분리해 담는 field는 protocol 차원에서
  명확히 추가하는 것이 좋다. 현재 gateway는 confidence/object_confidence를 object score로 둔다.
- web viewer는 desktop-hosted overlay를 볼 수 있으나, control에 필요한 것은 overlay가 아니라
  PATH_REMOTE_PERCEPTION_RESULT의 validated object/contact result이다.


3. Belief inference
===================

3.1 목적
--------

TASC-style belief inference의 목적은 다음 두 단계를 분리하는 것이다.

1) 상위 계층:
   - 어떤 object를 도울 것인가?
   - object posterior p(g)를 추정.

2) 하위 계층:
   - 선택된 object의 어느 contact/grip point를 목표로 할 것인가?
   - conditional contact posterior p(c | g)를 추정.

이 분리는 중요하다.
Shared control의 alpha는 "이 물체를 도울 확신"인 object posterior p(g*)로
구동하는 것이 안정적이고, contact posterior p(c|g)는 target contact point 선택과
평활화에 사용한다.


3.2 입력 feature
----------------

belief inference 입력:

- segmentation/tracking objects:
  - label
  - stable track_id
  - score
  - mask / box
  - center_goal_m
  - object point cloud
  - contact_candidates

- robot state:
  - q/dq
  - FK로 계산한 end-effector position P_ee
  - target_link 기준 local +X offset:
    - ee_offset_m=0.05

- operator/user action:
  - PICO wrist target 변화량 또는 user translation vector.
  - 현재 feature 계산에서는 action_apply_time=0.01 s로 짧은 미래 위치를 평가.

- robot-view ray:
  - PICO ray가 아니라 G1 robot camera view 기준.
  - depth/RGB image 중앙 방향을 카메라 좌표계의 고정 직선 ray로 두고,
    object/contact 방향 벡터와 내적/각도 cost로 사용.


3.3 feature cost
----------------

현재 feature 구성:

1) distance feature
   - P_ee와 후보 target/contact 사이 거리.
   - user action을 적용했을 때 거리가 줄어들면 positive advantage.
   - Huber-like distance cost 사용.
   - 파라미터:
     - w_distance=1.0
     - distance_k=1.5
     - distance_delta=0.10
     - distance_c=0.1

2) ray feature
   - G1 camera central ray와 object/contact 방향의 alignment.
   - camera view 중심 방향에 가까운 후보를 선호.
   - 파라미터:
     - w_ray=0.8
     - ray_k=1.0
     - ray_delta=0.15
     - ray_c=0.1

3) agreement feature
   - 사용자의 translation direction과 target direction의 agreement.
   - u_opt = kappa * n 형태.
   - 여기서 n은 G1 robot view ray / object-contact 방향 기반 단위 벡터.
   - user speed가 너무 작으면 feature를 0으로 둔다.
   - 파라미터:
     - w_agreement=0.6
     - agreement_lambda=1.0
     - agreement_kappa=1.0
     - min_user_speed_mps=0.005

4) delta feature
   - 현재 비중은 0.
   - 파라미터:
     - w_delta=0.0


3.4 robust standardization
--------------------------

advantage 값들이 모두 작을 때 MAD로 나누며 값이 폭증하는 문제를 막기 위해,
robust_standardize는 다음 안전장치를 갖는다.

입력 values에 대해:

  median = median(values)
  spread = max(values) - min(values)

  if spread < min_signal_spread:
      return zeros

  MAD = median(abs(values - median))
  scale = max(1.4826 * MAD, scale_floor, eps)
  z = clip((values - median) / scale, -clip, +clip)

현재 파라미터:

  min_signal_spread = 0.002
  scale_floor       = 0.01
  clip              = 2.0

의미:
  - 후보들 사이 신호 차이가 거의 없으면 belief update 자체를 0으로 둔다.
  - MAD가 너무 작아도 denominator가 0.01 아래로 내려가지 않는다.
  - standardized update는 [-2, +2] 범위로 제한된다.


3.5 상위 object Bayesian update
-------------------------------

object posterior:

  p_t(g)

log-space update:

  a_g       = feature advantage for object g
  z_g       = robust_standardize(EMA(a_g))
  log p_t   = normalize( w_sc * log p_{t-1} + beta * z_g )

그 다음 confidence-dependent leak-to-uniform과 max probability clipping 적용.

현재 파라미터:

  beta              = 1.0
  w_sc              = 0.95
  feature_ema_alpha = 0.25
  max_prob_any_goal = 0.99
  leak.kappa0       = 0.3
  leak.gamma        = 5.0

tracking:
  - label + 3-D nearest 기반 stable object id 사용.
  - object_track_max_distance_m=0.25
  - object_track_missing_ttl_frames=5


3.6 하위 contact/grip Bayesian update
-------------------------------------

각 object g마다 contact 후보 c_j를 만든다.

candidate 생성:
  - object point cloud / mask/depth 기반 surface point.
  - contact_candidates가 result에 있으면 그것을 우선 사용.
  - 없으면 center fallback 또는 point cloud 기반 후보 생성.

candidate 중복 처리:
  - 가까운 후보는 NMS 삭제가 아니라 radius merge 방식으로 병합.
  - merge_distance_m=0.03
  - weighted average center로 병합.
  - 병합 후 top_k 적용.
  - top_k=4

candidate persistence:
  - 이전 frame 후보와 3-D nearest-neighbor matching.
  - match_max_distance_m=0.04
  - missing_ttl_frames=3
  - 후보 id가 유지되므로 p(c|g)의 index swap 문제가 줄어든다.

contact posterior:

  p_t(c | g)

update는 object와 유사하게 log-space에서 진행:

  a_c          = feature advantage for contact c
  z_c          = robust_standardize(EMA(a_c))
  log p_t(c|g) = normalize( w_sc * log p_{t-1}(c|g) + beta * z_c )

grip update rate:
  - grip_update_hz=10

grip selection hysteresis:
  - switch_dwell_frames=2
  - switch_margin=0.0

diagnostic confidence:

  joint_confidence = p(g) * p(c | g)

중요:
  - joint_confidence는 log/diagnostic 용어이다.
  - shared control alpha에는 p(g*) object posterior를 쓰는 것이 목표이다.
  - 즉, 접촉점 후보가 흔들려도 "이 물체를 도울지" 판단이 흔들리지 않도록 한다.


3.7 optimal decision과 ZMQ 전달
-------------------------------

belief 결과에서 최종 decision:

  g* = argmax_g p(g)
  c* = argmax_c p(c | g*)
  p_contact = position(c*)

또는 구현 상태에 따라:

  selected target = argmax over valid object/contact candidate,
  confidence = object_confidence,
  joint_confidence = diagnostic.

ZMQ로 전달되는 target payload:

  endpoint: tcp://127.0.0.1:5564
  topic: path_static_ee_target
  coordinate_frame: pelvis_identity_fk
  target_link: left_wrist_yaw_link 또는 right_wrist_yaw_link
  position: p_contact 또는 center_goal_m
  quaternion: [1, 0, 0, 0] 기본
  streaming_goal: True
  confidence: object posterior 또는 현재 gateway에서는 YOLO score 기반
  object_id: stable track id

state machine은 이 target을 e/shared_control 모드에서 읽는다.
target이 null/stale이면 e 모드는 기본 human/PICO reference를 유지해야 한다.

[주의]
- 현재 remote gateway는 remote result의 object score를 confidence/object_confidence로
  재사용한다. desktop worker에서 belief posterior까지 계산한다면,
  protocol/result에 object_confidence와 joint_confidence를 명시적으로 넣고
  gateway가 object_confidence를 alpha confidence로 쓰도록 맞춰야 한다.

[미구현 / TODO]
- remote desktop worker가 YOLO segmentation만 할지, belief inference까지 수행할지
  최종 배치 결정 필요.
- belief까지 desktop에서 수행한다면 Thor는 validated target receiver 역할만 하고,
  Thor에서 object/contact Bayesian update를 중복 실행하지 않는 것이 깔끔하다.
- null target schema를 명확히 정의해야 한다.
  예: valid=True, objects=[], target=null 또는 explicit target_valid=False.


4. Shared control / action blending
===================================

4.1 입력
--------

Shared control 입력:

- human wrist reference:
  - PICO calibrated left/right wrist SE(3)
  - q/e 모두 같은 authoritative PICO wrist input을 사용.

- measured robot wrist:
  - current robot q에서 FK로 계산한 left/right wrist position.

- perception/belief target:
  - path_static_ee_target
  - p_contact 또는 center_goal_m
  - object_id
  - confidence


4.2 alpha 계산
--------------

현재 scripts/run_state_machine_bridge.sh 기본값:

  rho1 = 0.60
  rho2 = 0.90
  alpha_rate_up   = 1.0 / s
  alpha_rate_down = 3.0 / s
  v_transfer_max  = 0.25 m/s
  stale_after_s   = 0.3 s
  d_max_m         = 0.9 m
  ref_lpf_alpha   = 0.3

confidence c에서 raw alpha:

  if c <= rho1:
      alpha_raw = 0
  elif c >= rho2:
      alpha_raw = 1
  else:
      alpha_raw = (c - rho1) / (rho2 - rho1)

현재 rho1=0.60, rho2=0.90이므로:

  alpha_raw = 0                         when c <= 0.60
  alpha_raw = (c - 0.60) / 0.30          when 0.60 < c < 0.90
  alpha_raw = 1                         when c >= 0.90

rate limit:

  gap = ||p_contact - p_human_active||
  rate_up_eff = min(alpha_rate_up, v_transfer_max / gap)
  alpha_t = clip(alpha_raw,
                 alpha_{t-1} - alpha_rate_down * dt,
                 alpha_{t-1} + rate_up_eff * dt)

gating:

  - startup_hold_s 동안 alpha 상승 제한.
  - target age > stale_after_s이면 no fresh target.
  - gap > d_max_m이면 gap_too_large.
  - target invalid/null이면 alpha=0.


4.3 blended position target
---------------------------

active hand 선택:

- target_link에 left/right가 명시되면 해당 손 우선.
- 아니면 현재 measured wrist와 target의 거리로 가까운 손 선택.
- hand_switch_confirm_n=10, hand_h_margin_m=0.05로 손 선택 hysteresis.
- alpha가 활성화된 동안 lock_hand_while_active=True이면 손 switch를 막는다.

contact target smoothing:

  p_contact_lpf = (1 - ref_lpf_alpha) * p_contact_lpf_prev
                  + ref_lpf_alpha * p_contact_raw

현재 ref_lpf_alpha=0.3.

active hand blended target:

  p_ref_active = alpha * p_contact_lpf
                 + (1 - alpha) * p_human_active

inactive hand:

  p_ref_inactive = p_human_inactive

즉 e/shared_control에서 target이 확실할수록 active wrist target은 object/contact 쪽으로
가고, 확신이 낮거나 target이 없으면 순수 teleop wrist target으로 돌아간다.


4.4 optimization problem target으로 사용되는 방식
-------------------------------------------------

1. state machine이 PICO wrist target 두 개를 받는다.
2. e 모드에서는 active hand position만 p_ref_active로 교체한다.
3. inactive hand는 human/PICO target 유지.
4. 두 손 SE(3)를 CasADi/IPOPT bimanual IK에 넣는다.
5. IPOPT가 14-DoF arm q target을 푼다.
6. q_ref 29-DoF message로 감싸 path_qp_reference에 publish.
7. SONIC deploy runtime은 dynamic reference를 받아 최종 PD/action output에 반영한다.

[주의]
- q 모드는 teleop이므로 belief target을 먹이면 안 된다.
  q에서 IPOPT 경로를 쓰더라도 alpha=0, target blending 없음이 맞다.
- e 모드는 shared_control이므로 target이 fresh/valid일 때만 alpha가 올라간다.
- target confidence가 object score인지 object posterior인지에 따라 alpha 안정성이 크게 달라진다.

[미구현 / TODO]
- alpha confidence는 최종적으로 detector score가 아니라 object posterior p(g*)로 통일해야 한다.
- contact posterior p(c|g)는 alpha가 아니라 contact point 선택/평활화에만 사용해야 한다.
- remote worker와 gateway 사이 protocol에 object_confidence, joint_confidence,
  target_valid/null target을 명시적으로 추가하는 것이 다음 정리 과제이다.
